# 小家管理台第一版

线上入口：<https://kuma0595.github.io/Very-Three/admin/>

## 首次启用

1. 已有小屋数据库与登录账号保持不变。确认 `vt_members` 中 `id = 0` 的 Piggy 已绑定正确的 Auth 用户。
2. 在现有 Supabase 项目的 SQL Editor 执行 `supabase/admin.sql`。脚本可重复执行，不删除原照片；包含第四位成员 Zakery、共享房间权限及情侣相册六个新增槽位的兼容迁移。
3. 打开管理台，用 Piggy 已绑定账号的邮箱和密码登录。无需另外注册管理员，也无需把高权限密钥填进网页。
4. 如果之前已经打开页面，点击“重新检查”。普通家人账号会被拒绝进入管理台。

若 Piggy 尚未绑定账号，请先在 Supabase Authentication 创建登录用户，按现有 `bind-members.sql` 流程完成绑定后重新执行 `admin.sql`。账号创建与密码重置本版沿用 Supabase 用户管理控制台；管理台可以绑定其他成员的已有账号 UID，当前管理员自己的账号绑定不能解除。

## 已实现

- 小家概览与四位家人、待办计划、最近留言。
- 家人昵称、心情和已有登录账号 UID 绑定。房间归属按现有三室户型显示，本版不更改户型或成员角色。
- 三个房间的名称与介绍。
- 客厅八张共享照片、三个卧室各三个固定相框、Joey / Zakery 共用六张相册。支持上传、替换、移除、大图预览；客厅照片可调整顺序，最后四张展示在墙上。
- 所有成员的留言、计划新增、编辑、删除；计划完成状态。
- 欢迎标题、介绍以及按设备本地时间判断的白天开始 / 结束时段。主页约 30 秒同步一次，人物作息与视觉切换保持分离。
- 最近 80 次管理员操作记录。历史恢复、3D 布置编辑器和登录用户创建 / 密码重置不包含在本版。

## 权限和并发

管理员名单在 `vt_admin_users`，客户端不能写入。初次执行 SQL 从已绑定的 Piggy 账号初始化。后台每次读取快照和执行修改都由数据库端 `vt_is_admin()` 校验；前端隐藏页面不是权限边界。管理员必须仍是绑定的小家成员。

日常小屋的原有 RLS 保持不变。管理员内容修改通过 `vt_admin_mutate` 进行，所有分支都有管理员校验、输入范围检查、旧记录比较与行锁。有人先修改时拒绝覆盖，提示刷新重试。修改和操作记录在同一事务中保存。照片先上传到私有桶，数据库保存失败时清理新上传文件，成功后清理被替换的旧文件。数据库修改成功但旧文件清理失败时明确提示，不将成功的保存显示为失败。

管理台不包含 `service_role` 或 secret key。照片读取使用已登录成员的短期签名 URL。移除照片会删除对应文件；本版日志不提供文件恢复。

## 代码位置

- `dist/admin/index.html`、`admin.js`、`admin.css`：Vue 3 管理页面。
- `dist/admin/admin-api.js`：集中服务接口、身份检查、图片签名、上传补偿。
- `dist/home-settings.js`：主页对共享设置的读取及未迁移时的兼容。
- `dist/vendor/vue.esm-browser.prod.js`：本地托管的 Vue 3.5.22 浏览器生产构建，无需运行时 CDN。许可见同目录 `vue.LICENSE.txt`。
- `supabase/admin.sql`：数据库表、角色、管理 RPC、Storage 策略和操作记录。

## 以后迁移到自己的服务器

管理界面只通过 `admin-api.js` 获取快照与提交修改。可以先把整个 `dist/` 部署到自己的 Nginx，保留 Supabase 数据服务；再把 `admin-api.js` 的传输改为自己的登录、快照、修改、图片上传接口。

接口保留当前 `kind / key / action / data / before` 约定，服务器验证管理员身份并在事务中比较旧记录、写入操作日志。之后导出应用表数据、复制私有图片并替换存储适配器。认证可先继续使用 Supabase，避免一次性迁移密码系统。服务端密钥始终放在服务端。

## 验证范围

本地验证了 Vue 模板、八个页面和编辑表单、管理员与普通成员入口、登出竞态、CAS 参数、照片上传补偿、设置时间边界、目录路由和 SQL / PLpgSQL 语法。真实数据库授权及写入需在执行迁移后用实际账号完成首次验收。

可重复运行前端检查：在项目根目录执行 `npm run test:admin`。这些检查使用模拟数据，不连接或修改线上数据库。

## 家具与模型工作台

在管理台选择“家具与模型”。已有 Supabase 插件连接时可直接执行 `supabase/models.sql` 迁移；脚本保留现有布置。工作台只有管理员可访问，普通家人只读取已发布的模型库，不能读取草稿。

- 模型库：管理现有 34 款家具与墙饰的名称、介绍、默认配色、0.5–1.8 倍尺寸、碰撞开关、菜单显示与允许房间。隐藏款式不删除现有家具。
- 单件预览：复用小屋实际模型，支持旋转、缩放及昼夜预览。
- 房间预览：在三个卧室、客厅里新增、复制、收回自定义家具；点地面或输入 X/Z 调整，旋转为 90 度一步。家具自动贴地，墙饰固定贴在客厅后墙。固定墙体、门窗、原有床与内置家具暂不支持编辑；也不包含 GLB 上传。
- 辅助显示：蓝色外轮廓帮助判断体积，紫框表示选中家具；绿点由小屋实际寻路网格产生，表示人物可站立的位置，并非完整的路径可达性保证。新摆放和修改过的模型会经过房间边界、物件重叠、门口留白和出入口连通检查。
- 保存草稿：仅管理员工作台可见。草稿覆盖四个空间，保留颜色和所有单件 ID。
- 应用到小屋：先检查摆放，再在数据库同一事务内发布模型库和四个空间的布置。小屋约 10 秒同步；正在布置的家人如果使用旧版本保存，会提示版本冲突。
- 恢复上一版：恢复上次发布前的模型库与四个空间，保留一次可恢复快照；不是无限版本历史。发布后若家人修改过任一空间，则停止恢复，避免覆盖。
- 多设备修改：草稿版本与四个房间版本同时校验。出现冲突时，可选“从小屋重新开始”清除草稿并载入最新布置；“重新载入”只载入服务器已有草稿。

模型数据入口独立在 `dist/admin/model-api.js`，已发布模型配置在 `vt_model_catalog`；草稿及恢复快照在 `vt_model_workspace`。模型管理操作写入现有 `vt_admin_log`。默认尺寸对未设置独立尺寸的已有家具也生效；明确设置独立尺寸后，单件设置优先。

### 验证

`npm run test:admin` 和 `node scripts/check-navigation.mjs` 不需要额外依赖。真实 WebGL 浏览器回归使用 Playwright：安装后运行 `npm run test:models:browser`，也可以通过 `VT_PLAYWRIGHT_MODULE` 指定模块路径、`VT_CHROME` 指定 Chromium 可执行文件。可选 `VT_SCREENSHOTS` 输出截图目录。浏览器回归使用模拟账号与接口，不写真实小屋；数据库草稿、发布、恢复、版本冲突、RLS 权限已另外在回滚事务内验证。

安全检查提示这些管理 RPC 使用 `SECURITY DEFINER`：这是为了在完整管理员校验后原子发布多个房间；匿名角色没有执行权限。两个 RPC 均在入口调用 `vt_is_admin()`，并固定空 search_path。请保留这些校验，不能直接向网页开放高权限密钥。

数量上限：客厅最多 30 件（含墙饰），三个卧室各 12 件。已有项目可执行 `supabase/living-decor-limit.sql` 更新校验，不清空现有布置。

家具互动已接入布置模型：凳子、坐垫、双人沙发、扶手椅和长凳可点击坐下，尺寸与旋转沿用实例设置。后台修改或收回家具时，正在走近或坐着的当前角色会取消互动或安全起身。主页面固定椅子、餐椅、庭院长凳和三个卧室的床也可互动；床按所属房间使用，Joey 与 Zakery 各使用共享床的一个位置。占用判断来自当前浏览器中的角色状态，不提供跨设备实时座位预约。
